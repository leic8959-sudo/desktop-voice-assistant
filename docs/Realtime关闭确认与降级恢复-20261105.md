# Realtime 关闭确认与降级恢复（2026-11-05）

## 问题与独立证据

`VoiceSession.connect` 原本已经先 await 失败后端的 close，再尝试下一个已配置供应商；顺序本身正确。问题在于 `RealtimeBackend.close` 把关闭异常仅记为 debug 后吞掉，也不核对返回后的 closed 状态。主代理独立复现 `evidence/realtime-close-fallback-reproduction-20261105.json`：受控旧 cloud.close 抛 OSError、closed 仍为 false 时，新 fallback 仍 connect 一次并被选为当前后端。这证明缺少关闭失败的传播与裁决，不证明真实云端已经出现同样重叠。

已安装 aiohttp 为 3.12.15。只读源码确认默认 ws_close 为 10 秒，期限仅包回复 CLOSE 的 reader 等待，未覆盖 writer.close 及 receive 的 close_wait。主代理本机 aiohttp 基线 `evidence/realtime-real-close-baseline-20261105.json` 记录 peer 已收到 CLOSE、未回 CLOSE 时 backend.close 仍等待；取消后真实 client.closed 为 true，但当下服务端 transport.is_closing 仍为 false。不能用本地 closed 标记即时推断对端 transport 已关闭，最终本机测试另外等待服务端 transport 进入 closing。

Realtime 握手使用的共享 HTTP 会话已有 total=20、sock_connect=10，aiohttp 较长期限取整可能带来不足一秒调度余量，不是默认五分钟或无界等待。原 shield 后等待握手清理、NativeDevice 等待旧 owner 完成，属于既有安全设计。本轮不修改握手取消策略、供应商顺序、原生 owner 或唤醒门禁，也不根据旧拒绝记录归因当前设备行为。

## 最小实现

生产仅改 `gateway.py` 的两个原方法，新增一个固定常量 `REALTIME_CLOSE_TIMEOUT = 3`，不新增配置或依赖。

- `RealtimeBackend.close` 用 3 秒总 timeout 覆盖整个 cloud.close await；返回后核对 closed。普通关闭异常、总期限到期或关闭未确认均保留完整堆栈并传播，取消原样传播，保留 cloud 引用用于排查。`VoiceSession.connect` 原有的失败后端 close 在 continue 之前，关闭失败自然阻止本次 fallback，不建立后台旧连接任务、不关闭共享 HTTP client、不通过私有 transport 属性强制终止。
- `VoiceSession.close_resources` 用嵌套 finally 保证尝试关闭 backend 后仍执行设备代理 socket.close，并始终清空 run_task；interrupt、backend 或设备关闭失败均传播，双失败保留 Python 异常链。只有全部清理成功才记录原 session_closed；任何失败（含取消）记录 session_cleanup_failed 与完整堆栈，不把清理失败写成关闭成功。

NativeDevice 的容量和 owner 清理继续沿既有流程运行，不增加全局停用开关。真实本机关闭确认与后续原生回合恢复通过测试检查；这不等同于云端计费、设备播放或真人唤醒验收。

实施代理独立只读比对 round19 候选列出的 14 个生产文件：仅 gateway.py 哈希改变，其余 13 个相同。使用 Python ast 读取定义、忽略行号比对，变化仅为 `RealtimeBackend.close`、`VoiceSession.close_resources`；没有新增或删除方法。Realtime 构造/connect/wait_cloud、VoiceSession 构造/connect/run，以及 lifecycle、create_app、handle_native_device、open_session 的原 AST 均未改变。不能据此泛称“整个启动或恢复行为不变”：原 connect/run 仍会调用本轮改变的清理方法，关闭失败传播、fallback 被阻止和失败日志正是预期行为变化；正常启动、配置加载、共享 HTTP 创建及原生 owner 的实现边界保持。
