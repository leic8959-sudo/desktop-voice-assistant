## 能力与音频格式

设备 hello 新增 `features.media_stream=true`；`features.media_wake_word` 只有离线唤醒初始化成功且软件 AEC 可用时为 true。旧固件缺少能力时，网关应明确提示需要升级，不能沿用 TTS 冒充设备媒体播放。AEC 不可用时仍可用 BOOT 按键，但不声明音乐期间可语音唤醒。

播放格式固定为 24kHz、单声道、16bit little-endian PCM。20ms 是 480 个样本、960 字节；1920 字节是 40ms，不是 20ms。复用现有 I2S、codec、软件 AEC 参考和 `audio_play_pcm24`。没有新增歌曲缓存、解码器或大音频缓冲，没有在设备加载整首歌曲。

既有音频队列 `AUDIO_QUEUE_CAPACITY=32`，每个 `AudioChunk` 数据容量 2048 字节；媒体单个 WebSocket binary 消息最多 960 字节，所以正常媒体缓冲约 640ms，再加一块正在写出的帧。`queue_used` 是当前等待块数，不包括播放任务正在写出的帧。新增的只是 4 个媒体元数据命令和 8 个小型回执，均有界且队列载荷放 PSRAM；不新增常驻任务，回执复用现有 screen_actions 任务。

## 网关到设备

开始示例：

```json
{"type":"media_start","playback_id":"music-unique-id","format":"pcm_s16le","sample_rate":24000,"channels":1,"frame_duration_ms":20,"position_samples":0,"title":"歌曲名称","duration_s":180}
```

- `playback_id` 必须为 1～63 个 UTF-8 字节，不接受控制字符；网关使用唯一 ASCII ID。
- `title` 可省略，最多 192 个 UTF-8 字节，不接受控制字符；为空时显示媒体播放提示。屏幕保留 Speaking 动画，标题改为“正在播放”。
- `position_samples` 必填，为从音源起点计算的非负整数，最大 2,073,600,000（24 小时）。它是继续播放时的绝对起点，不是本次新增播放量。
- `duration_s` 可省略，若存在则为 0～86400 的整数，只作为受限元数据；设备不按它虚构进度或自然结束。
- `format/sample_rate/channels/frame_duration_ms` 必须与示例完全一致。start 只允许示例中的 9 个字段，拒绝未知字段；URL、路径、Token 均不进入设备媒体协议。

设备确认 codec 已打开且媒体模式就绪后回 `start`。这表示可接收 PCM，不表示喇叭已出声。网关必须等待 start 成功回执后才发送 binary，每消息一个 960 字节帧，末帧可以为更短的偶数字节。固件不拼接奇数字节分片，不接受超过 960 字节的媒体消息。媒体 binary 不再加 JSON 包装，由当前媒体模式区分；普通 TTS 和媒体不能并发发送。

其余控制均绑定同一播放 ID：

```json
{"type":"media_pause","playback_id":"music-unique-id"}
{"type":"media_stop","playback_id":"music-unique-id"}
{"type":"media_end","playback_id":"music-unique-id"}
```

`pause/stop` 在播放任务中处理：当前 write 返回并计数后，更新 generation、清空待播放队列、执行 `audio_playback_abort` 静音，再发回执。因此回执位置在暂停后稳定，不把收到的数据当作已播放。相同 ID 的重复 pause/stop 可回同一位置，不再次启动播放。新的 start 遇到语音、提示音、升级或已有媒体时返回 `audio_busy`；相同活动 ID 的重复 start 只重发 start 回执，不重置位置。

`media_end` 表示网关已发送最后一个 PCM 帧。设备关闭后续 binary 接收，等待现有队列全部写完才回 `ended`；自然结束不做 abort/mute，保留 codec/I2S 尾音。停止与自然结束不同，不能把 pause/stop、断线或失败报告成 ended。显式继续需要重新 start，并使用已确认的绝对位置；设备不会擅自续播。

## 设备到网关

```json
{"type":"media_ack","state":"progress","phase":"progress","playback_id":"music-unique-id","played_samples":24000,"position_samples":24000,"underruns":0,"queue_used":4,"queue_capacity":32}
```

`state` 与兼容字段 `phase` 同值：`start`、`pause`、`stop`、`progress`、`ended`、`error`。活动媒体约每秒产生 progress；所有状态都带播放 ID、绝对样本位置、underruns 和队列容量。错误还带固定 `error`，不回显网络地址、凭据或原始任意错误文本。

`played_samples` 与 `position_samples` 都等于 start 起点加上本次 `audio_play_pcm24` 成功写入的 PCM 样本数。网关位置直接取 `played_samples / 24000`，不得再次加 start 起点。计数不包括接收但尚未 write 的队列，也不因时钟流逝自行增加。驱动只返回 write 成功码，没有 DAC 呈现位置或物理听音回读，所以这里表示成功交给 codec 的样本位置，不能宣称每个样本已经从扬声器出声；暂停可能有硬件尾音。

`underruns` 统计已开始播放后发生的缺帧和重新预缓冲次数，初次等待不算一次 underrun。队列溢出不丢帧继续假装成功，直接停止该媒体并回 `audio_queue_full`。其他错误包括 `invalid_playback_id`、`invalid_audio_parameters`、`unknown_start_field`、`command_queue_full`、`stale_playback_id`、`audio_busy`、`audio_not_ready`、`invalid_media_frame`、`audio_write_failed`、`position_limit` 和 `media_not_active`。回执队列满会记录错误并让网关超时；不会编造成功。

回执先保存稳定元数据，再由既有 screen_actions 任务做有超时的 WebSocket 发送。采音任务和播放任务均不因 media_ack 的网络等待而阻塞。断线后清媒体命令、停止媒体且不自动重播；未收到明确回执时网关应呈现未知/失败，而不是推断已经播放或暂停。

## 音乐期间完整唤醒词

原 `kEnableBargeIn=false` 保持不变，普通回答期间仍不跑普通语音打断。新增独立媒体分支使用现有 AEC 后采音、4 秒前置缓存和 2 秒后置缓存，不新增唤醒音频大缓存。

媒体期间不会持续上传歌曲/麦克风音频到云端。高相关回声或不可用的采音指标不喂真实口令帧；完整本地口令命中还需 800ms 内有近端人声迹象，才登记暂停候选。采音任务只排命令，不做媒体回执网络等待。播放任务暂停并稳定样本位置后，网络任务先发送 `pause`，附 `reason=wake_word`，再沿原流程发送 `listen.detect`（含 wake_id）、`listen.start` 并上传同一唤醒缓存，继续由网关 ASR 校验完整口令。

本地命中只说明候选，不能代替服务端校验；服务端也不能把本地候选直接作为真人授权。AEC/相关性和 ASR 无法从原理上证明声源一定是真人，尤其音轨本身包含完整口令、混响或外部音箱时，仍需真实设备验证。媒体停止后的待机唤醒抑制 400ms 尾音；进入语音会话后沿用原 400ms 上行静音窗，避免歌声尾音触发云端自问。

BOOT 按键在媒体模式同样先 pause，`reason=button`，随后进入原手动听音；不绕过任何第三方写入或账号授权。无论候选最终通过或拒绝，媒体都保持暂停，只有明确继续才恢复。
