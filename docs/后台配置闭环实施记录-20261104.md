## 界面和接口交付

控制台连接器页使用服务端白名单元数据生成真实字段表单；字段标注配置来源、有无值和是否可编辑。秘密始终为空的密码框，留空保留，只有勾选明确清除才覆盖为空。提交完成或失败都会清空秘密输入。保存状态、OAuth 状态和连接检查结果分开显示；配置保存不作外部调用。

`GET /api/connectors/{id}/config` 只返回元数据和非秘密值。除 Gmail 外，保存使用 `POST /api/connectors/{id}/config`，正文仅允许 `values` 与 `clear_fields`。未知字段、其他连接器的字段、设备凭据、文件路径、任意配置 patch、错误类型及不允许的清除都会拒绝。Gmail 保存继续调用既有 `POST /api/gmail/config` 和同一 DPAPI 文件、配置锁、OAuth 回调及发送确认，不另建 Gmail 凭据系统。

## 存储、优先级与并发

1. 连接器及模型白名单：**环境变量 > 后台安全覆盖值 > 启动 JSON**。Gmail 的专用 DPAPI 值同样不能覆盖受环境变量管理的字段；Gmail 元数据从实际 GmailService 配置读取。语音 / 人格 / 供应商选择沿用各自既有偏好文件。
2. 环境读取集中在配置加载边界，字段通过 `ASSISTANT_<字段名大写>` 注入；UI 标注并禁用这些字段，后端也拒绝覆盖。布尔 / 数字环境字段在边界转换和校验。
3. 复用 `DpapiTokenVault` 的 Windows 当前用户加密。写入使用独立临时文件、flush、fsync 和 `os.replace`；失败不更新运行字典。所有后台配置写入通过跨请求锁，HA 还与完整家居操作串行，避免中途更换 URL / Token。Gmail 仍使用独立配置锁 / 服务锁，并在应用失败时回滚原专用保存值。
4. 明确清除持久化为空覆盖标记，而非删掉覆盖项；重启后不会让旧 JSON 中的秘密重新出现。
5. 非 Windows / Docker 没有本轮安全秘密持久化提供方时，秘密表单只读，必须使用部署环境变量；不会明文降级。已有加密覆盖文件不可读取时阻止错误恢复，不静默把它当成功。秘密配置与文件 / 存储内部错误均不把秘密写进响应或审计。
6. 新配置写 API 经过现有管理员认证和同源校验。HTTP 秘密提交仅允许真实 loopback peer + loopback Host 且不经过 Forwarded 代理；远程必须是服务实际 TLS 连接，不能用 `X-Forwarded-Proto` 冒充。Gmail 专用配置仍遵守原有仅本机边界。
