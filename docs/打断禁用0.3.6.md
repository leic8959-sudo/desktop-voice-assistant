# 2026-11-02：0.3.6 暂时禁用语音打断（barge-in）

牛牛反馈（0.3.5 上机后）：**"自然对话还可以，打断不行，先把打断禁用吧"**。0.3.6 因此把语音打断整条链路关掉：回答一定完整播完，播完后再听用户；0.3.5 的自问自答修复（400ms 尾音静音窗口）保持不变。

## 为什么"打断不行"

0.3.4 起为了掐断"回声→云端 VAD 误判→回答-打断循环"，播放期上行就一直是静音帧（0.3.3 实测结论）。这带来两个后果：

- 云端 VAD 在播放期根本听不到用户，云端介入式打断不可用。
- 本地两条打断通道也不可靠：本地强打断要求"连续 400ms clean_rms>3000"，与 AEC 残留峰值区间接近，容易误触发或触发不了；唤醒词打断在 0.3.4 代码里喂给 `wake_word_feed` 的其实是 `memset` 后的静音帧，等于不生效（播放期 MN 推理本身也超帧周期）。
- 0.3.5 又加了播放结束后的 400ms 尾音静音窗口，可打断窗口进一步收窄。

结果就是打断整体不可用，且偶发半截停顿（本地强打断/残留误判）体验更差。先禁用是合理的过渡。

## 0.3.6 改动

`firmware/assistant_espidf/main/control_protocol.cpp`：

- 新增编译期总开关 `static constexpr bool kEnableBargeIn = false;`（L105-114）。
- 采集循环 speaking 分支改为 if/else：
  - `false`（当前）：只 `memset(frame,0,bytes)` 上传静音帧、`g_loud_hold_us=0`；不再 `cache_barge_audio`、不跑 `kLoudInterruptRms` 本地强打断、不喂唤醒词、不触发 `start_barge_candidate/confirm_barge/abort`。

- 0.3.5 修复保留：`kUplinkEchoTailUs=400000`、`note_playback_stopped()` 及全部停播路径。
- 物理 BOOT 键（GPIO0）路径不受影响：按下仍会 `control_protocol_listen_start()` → `begin_listening(true)`，播放中会先 abort 当前回答。

## 当前行为（0.3.6）

- 回答播放期间：不说话被识别、不缓存打断音频、云端只收到静音；**回答一定播完**。
- 播完后 400ms（尾音窗口）内开口：开头会被吞，之后正常进入下一轮。
- 播完后正常说话：自然对话不受影响（0.3.5 已验证的链路）。
- 播放中用户说的话**完全不会进入云端**，不会在播完后自动补听。
- 想中途停：按物理 BOOT 键（会 abort 当前回答）。

## 恢复语音打断的方式

1. `kEnableBargeIn = true`，重新构建并 OTA。
2. 恢复前建议先解决两个前提（见 `docs/自然插话尝试与播放期打断失稳20261101.md`）：播放期 MN 推理实时性、云端 VAD 对 AEC 残留的误判；或者改走"播放期持续上传 + 网关侧回声判别"的路线，而不是本地强打断。

## 风险与待验收

- 长回答只能等播完（或按 BOOT 键），这是本轮明确取舍。
- 待牛牛实机确认：播放中说话不再被打断/不再半截停顿；播完接着说话能正常应答。
- 若日后误把 `kEnableBargeIn` 改回 true 但没修根因，0.3.3 的"回答-打断循环"和本轮"自问自答"都可能复发。
