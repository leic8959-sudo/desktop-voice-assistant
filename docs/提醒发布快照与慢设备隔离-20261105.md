# 提醒发布快照与慢设备隔离（2026-11-05）

## 源码与独立复现

原通知循环在 `claim_due_reminders` 提交并返回的等待窗口后，直接把每个旧行重新插入缓存并发送。完成、取消、稍后提醒等本地入口虽然在存储成功后清除同一缓存，但候选尚未登记时只能 pop 空字典，随后旧领取行仍可能复活。重连路径先获取缓存 tuple 再逐个等待发送，期间被确认或移除的后续通知也可能继续发送。

主代理独立受控基线 `evidence/reminder-stale-claim-reproduction-20261105.json` 证实任务已经 completed、数据库租约被清除后仍发出一条旧通知并留在缓存。`evidence/reminder-slow-device-reproduction-20261105.json` 另证第一设备发送挂起时，第二设备通知数及 timer_snapshot 次数均为 0，worker 停在没有期限的发送等待。

实际执行初始 `python -m unittest tests.test_reminder_publication`：9 项，7 个失败、1 个等待超时错误、1 个对照通过，1.982 秒、退出 1，日志 `evidence/reminder-publication-20261105-before.log`。等待超时来自第二设备被首个无期限发送堵住；整目标批次预算对照在原 row-major 顺序下能通过，不能把九项全部说成原逻辑缺陷。

## 最小实现与资源范围

仅修改 `assistant_core/store.py` 和 `assistant_runtime.py`。Store 新增最多 100 个候选的租约快照复核，强制使用现有任务 ID 主键索引，按有限 task_id IN 查询并保留 device_id 隔离及候选数量 LIMIT；随后仅在这些行中比较 pending/leased 状态、实际到期及租约期限、token、updated_at。没有每行查询、全设备积压扫描、新表或索引。主代理只读 EXPLAIN 曾发现默认优化器可能走设备到期索引，故不能仅凭 IN 或“用了某个索引”假定有界。

通知循环先在既有有界缓存登记 `validating` 候选，再等待批量数据库复核；复核通过且缓存仍为原候选对象才转为 pending_delivery。现有 API、语音及屏幕操作成功后的 pop 可以使候选失效，不会在验证返回后重新插回旧行；验证失败或取消时只清除本批仍属自己的临时状态，不删除新租约。状态 API、ACK 和重连均不把 validating 当可交付通知。

每个设备扇出前再次批量复核候选，完整等待该次数据库读取后才开始网络发送预算，设备内顺序发送。一个共享常量 3 秒同时限定单次发送（等待发送锁和 socket）以及该目标整批的网络发送总等待；目标发送超时或写失败后停止其本批余项，继续其他设备及定时卡，不创建并行任务。数据库锁及 SQLite 忙等待仍按既有 Store 机制处理，不属于 3 秒网络预算；不能靠取消 to_thread 的等待留下仍在运行的数据库查询并提前开始下一批。取得发送锁后再次检查当前缓存对象、token、版本、期限与设备在线状态，避免此前慢等待期间已移除或过期的通知发送。领取候选为空时直接返回，不进入验证线程。

设备重连复用同一批量复核和有界发送路径。ACK 存储成功后，仅当前缓存仍是该次 ACK 捕获的原对象时移除，避免迟到的旧确认删除已替换的新租约缓存。数据库租约验证仍是授权来源，ACK 不代表待办完成。

## 保证与不保证

覆盖在最终数据库复核前已经失效的候选，以及在本地缓存移除、版本更换或期限过后尚未进入 socket 发送的通知。最终检查后到网络传输、设备显示之间的状态变化无法撤回；发送超时也不能证明设备未显示。本轮是单实例应用缓存裁决，不承诺跨进程 exactly-once 或撤销已显示卡片，没有新增固件撤回协议。

正常领取意味着提醒已到期，而改期原合同要求原提醒仍在未来，因此不制造“正常 claim 后 reschedule 成功”的虚假竞态，也不放宽 CAS。完成、取消、稍后提醒、旧 ACK、租约到期和重连边界以真实存储及缓存行为验证。未 ACK 的有效缓存不会因为发送超时被假确认，仍沿原租约到期重领流程处理。
