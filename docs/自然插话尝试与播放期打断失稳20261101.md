# 2026-11-01：自然插话尝试、播放期打断失稳与回退（0.2.7-0.3.1）

牛牛反馈两轮：打断有问题（复现为误打断，已修，见 1031 文档）；"打断用不了，不能像 GPT 那样自然打断"。本轮尝试重新启用自然插话并排查播放期打断，最终回退到单通道（唤醒词打断），原因与数据如下。

## 尝试与数据（全部经 OTA 推送，0.2.5→0.2.6→…→0.3.1 六次自动升级）

- **0.2.7/0.2.8（自然插话启用）**：触发/确认同门槛（clean_rms≥2500 且相关<0.6）、暂停期收音增益 30dB、candidate 后不 continue 修 MN 饿死。实测：**回答不再被取消（确认判据兜底正确）**，但残留峰值帧造成 4-8 次"暂停-恢复"顿挫（每次 700ms，听感差）；且唤醒词打断通道完全失效。
- **关键发现：MN 推理暴涨**。待机基线 15ms（mn6），自然候选循环期间 **avg 43-76ms、峰值 183ms**（帧周期 32ms）——MN 处理不过来，播放期唤醒词帧丢失，喂入正常（pending_resets=0）但零 DETECTED。
- **0.2.9/0.3.0（回退自然逻辑、NS 开→关）**：关 NS 推理仍 26-66ms——NS 不是推理暴涨主因；播放期 CPU 竞争（candidate 空转/播放任务/渲染争用 PSRAM 带宽）嫌疑最大，需专项 profile。
- **0.3.1（当前）**：单通道唤醒词打断（阈值 0.30、无 NS、AEC VERYAGGR 保留）。配对测试播放期唤醒词打断仍不稳定（0.2.6 时代同场景一发即中），**根因是播放期 MN 实时性，不是阈值**。
- 期间顺带修复：两个测试脚本（barge/chime）接入 device_pong 应答，测试期间不再触发设备 240 秒下行看门狗；自然插话参数（kNaturalBarge*）与 g_barge_natural 来源标志保留在代码中，便于专项轮重启。

## 当前状态（0.3.1）

- 唤醒 ✓、对话 ✓、误打断已修 ✓、OTA 链路 ✓（本轮六次升级全部自动完成，USB 一次未接）。
- **播放中说唤醒词打断：不稳定**——专项轮的第一优先级，方向：播放期 MN/推理任务优先级与 CPU profile、candidate 期间暂停 MN 喂入与检测的调度策略、或评估 AFE 内置 wakenet 方案。
- **自然插话（GPT 式）：暂缓**——依赖播放期打断实时性解决后再启用，参数已备好。

## 0.3.2：自然打断改走云端 VAD（小智/HA PE 同款架构，牛牛指令"看现成方案"的产出）

调研结论：本地 MultiNet 播放期打断是算力死角（26-76ms>32ms 帧周期），而**业界方案（小智 xiaozhi-esp32 v2.5.2 源码核实、Home Assistant Voice PE）的 GPT 式打断都是"播放期持续上传音频，由云端 VAD 判定用户开口后取消回答"**——我们的 Realtime 协议里这条链路本来就是通的（gateway 处理 `input_audio_buffer.speech_started` → `interrupt()`，昨天日志里 device_interrupt 多次成功），**设备端缺的只是：播放期把麦克风上传静音了（发全零，云端 VAD 永远看不到用户说话）**。

0.3.2 改动（control_protocol.cpp）：

- speaking 期恢复上传：去掉 memset 清零，改为**本地残留门槛过滤**——AEC 后残留实测 400-800（echo_floor 1195），真人 12dB 下 3000+，`clean_rms < 1200 置零上传`（kUplinkSilenceRms），防止回声残留触发云端 VAD 误打断。
- 唤醒词打断保留为兜底通道（MN 播放期推理慢，仅兜底）。
- 清理 0.2.7 的自然候选死代码（g_barge_natural/kNaturalBarge*/确认分叉），BARGE_VOICE_CONFIRM 回 120ms。

验证：OTA 推送 0.3.1→0.3.2 成功（app0 读回 0.3.2），设备在线。**云端 VAD 自然打断的效果需真人会话实测**（播放中说"等一下"应取消回答并响应新内容；电视/背景声可能触发误打断，门槛 1200 与云端 VAD threshold 0.5 是后续调优点）。

## 0.3.3：三层打断架构（三通道录音推翻逐帧置零方案）

三通道录音（0.3.2 实测）推翻残留假设：**播放期 AEC 残留不是恒定 400-800，而是 0-7000 剧烈波动**，与人声区间大量重叠——0.3.2 的逐帧 RMS 置零造成上传音频破碎失真，云端 VAD 收到断续音频不触发（牛牛实测"不管用"的机制）。

0.3.3 定型三层架构：

1. **云端 VAD（主通道）**：播放期上传 AEC 原声（不再逐帧置零），gateway 的 `server_vad threshold 0.5→0.75` 抑制残留误触发；检测到用户开口发 speech_started → interrupt 取消回答。
2. **本地强打断（辅）**：持续 400ms 超过 clean_rms 3000 直接本地取消（残留峰值帧稀疏难持续 400ms；真人连续说话稳定触发）。
3. **唤醒词（兜底）**：阈值 0.30，播放期 MN 推理 26-76ms 超帧周期，仅兜底。

OTA 推送 0.3.2→0.3.3 成功，设备在线。

## 0.3.4：终止"回答-打断"循环，自然打断完全本地化

牛牛实测 0.3.3 陷入无限循环：日志显示**每次回答开始 1-2 秒即被打断 → 云端重新生成 → 又被打断**（54a2 会话 10:52:23-26 三连），bridge 无 barge/interrupt 日志 = 打断来自云端 VAD——**回声残留本质是语音的复制品，上传给云端 VAD 后 0.75 阈值也挡不住，且打断后云端重新生成的回答又被残留打断，形成循环**。云端 VAD 路线被实测否决。

0.3.4 定稿：

- **播放期上传恢复静音**（回 0.2.6 形态），从源头掐断云端误触发循环。
- **自然打断完全本地化**：持续 400ms 超过 clean_rms 3000 → 本地 candidate→confirm→取消回答→进 listening（上传恢复，云端正常收新内容）。残留峰值帧稀疏（1 秒约 1 帧）凑不满连续 400ms，不会误触发；真人连续说话稳定触发。
- 唤醒词兜底保留（0.30）。

OTA 推送 0.3.3→0.3.4 成功（app0 读回 0.3.4），设备在线 idle。

## 当前状态（0.3.4）与待实测

- **待牛牛实测**：①回答时**连续说 400ms 以上**（正常说半句话即可）能否打断并接新内容；②背景声/电视下是否还会自己停（若仍误触发，kLoudInterruptRms 3000→3500 或 HoldUs 400→600）。
- 已知边界：打断需要"连续 400ms 高电平"，单个短词（"停"）可能不够长——真有需求可降 HoldUs，代价是误打断风险上升。
