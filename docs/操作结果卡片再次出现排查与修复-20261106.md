# 操作结果卡片再次出现：排查与修复（2026-11-06）

牛牛明确指出：小燕子实体屏幕显示的是独立“操作已返回结果”卡片，并非底部旧状态提示。先前仅根据固件残留文案作解释不足，不能用它否定实际观察。

## 已确认和未知

- 现网网关 PID 27396 来自 `runtime/releases/voice-boundaries-0322-20261106/launch_gateway.py`，设备报告 0.3.22。检查时发布清单 110 个工作区文件哈希一致，没有证据表明此次是重新运行旧网关。
- 当前 `operation_screen_feedback` 只写有界后台完成记录、不发卡；`send_home_screen_card` 是 no-op。另只读检查本地 Python 字节码，前者没有 send 函数引用，后者没有调用引用。此项用于排查本地缓存代码差异，不能代替读取正在运行进程的实际内存。
- 通用反馈转换器仍可生成 `kind=task,status=completed`；固件接收端仍接受 task/home 结果状态、存入普通信息卡与最多三项待显队列，并将 completed 显示为“操作已返回结果”。这是明确的接收/显示防线缺口；其存在不证明本次某个具体业务入口确实重新下发。
- 检查时网关只保留最新一次显示回执，旧日志没有完整的卡片下发类型、状态和来源。16:59:57 的 shown 回执早于 17:06 空调请求，后续又有设备重连；不能据此断言卡片来自刚才空调、旧缓存或某个后台事件。
- 固件确有两句旧提示：“操作结果会显示为卡片”“结束后显示操作结果”，但牛牛已明确它们不是本次观察对象。修复中一并更正文案，不将其冒充独立卡片的根因。

## 修复边界

沿用已确认的人工决策：禁用通用操作/家居结果卡，后台结果记录保留，专用提醒、计时、天气等仍独立工作。不把本次问题扩大为关闭所有卡片。

1. 网关统一发送入口阻止非 timer/reminder 卡片中带非空结果状态的操作反馈；clear 是清除命令，允许通过。父复核发现 completed 标题映射对所有类型均生效，只挡 task/home 会漏掉其他信息卡类型，因此最终策略不依赖未知生产者的 kind 假设。已逐项核对现有专用 task/home/weather/today/route/power 生产者均不携带结果 status，timer 使用既有专属状态。禁止发送时返回 disabled/零发送，不将其说成已送达，不影响原业务操作结果。
2. 设备收卡入口使用相同策略拒绝；显示前清理当前和待显队列中的同类结果，防止被屏蔽后从待显队列恢复。明确保留 timer/reminder 及未携带结果状态的专用信息卡。不是仅隐藏“操作已返回结果”这句标题，整个已禁操作反馈卡片都不入队、不显示。
3. 卡片日志仅记录 ID、类型、状态、固定来源标识和回执，不能记录标题、正文、业务内容或凭据；关联状态有界，不凭未知回执编造来源。
4. 两句旧状态提示分别改为“可以继续说话”和“正在播放回答”。
