# 打断阈值、状态提示音与过渡动画

本轮由牛牛提出三点：提示词唤醒与打断对话仍需优化、状态过渡动画太少、联网搜索和思考时没有提示音。针对第一点先做了机制上确定的两项改动，第二、三点为纯新增功能；真人唤醒率仍需实机验收。

## 已修改的代码（均在 firmware/assistant_espidf/main）

- `wake_word.cpp`、`wake_word.h`：
  - 首选模型改为 `mn6_cn`（高质量版），分区没有时回退 `mn5q8_cn` 并保持历史阈值 0.20。当前分区只烧了 mn5q8，回退路径行为与上一版完全一致；烧录 mn6 模型包后自动启用。
  - 新增 `wake_word_set_threshold(float)`，运行中可切换检测阈值。
- `control_protocol.cpp`：
  - 播放期间（含候选暂停期）唤醒阈值降到 0.12，回待机恢复 0.20。机制依据：播放时麦克风增益从 30dB 降到 12dB，人声进入 MultiNet 的电平低 18dB，是打断必须说完整唤醒词却常常无效的直接原因之一；打断是显式意图，宁可低门槛也不漏打断。
  - 新增本地状态提示音：进入"想一想"或"正在处理"（含搜索）时播放两声上行"叮咚"（988Hz→1319Hz，约 250ms，音量约 -15dBFS）。服务端连续推送同一状态只响一次；回答播放期间收到推送不抢当前音频，等播完后补响。提示音走既有播放链（audio_play_pcm24），AEC 参考自动对齐，不会造成回声误唤醒，打断提示音会被正常取消。
- `display_ui.cpp`：
  - 状态切换时标题与详情文字 240ms 淡入；状态点常亮呼吸（1.3s 周期，只重绘 5x5 小区域，不影响待机跳帧预算）；状态切换瞬间粒子云有一次激发脉冲（半径 +10% 后指数回落）。

## mn6_cn 模型包（未烧录，待牛牛决定）

- 已用隔离构建卷 `assistant-idf-sr247-v1` 内的 ESP-SR 2.4.7 组件离线打包：`runtime/wake_samples/srmodels-mn6_cn-sr247.bin`，3,703,659 字节，4MB 模型分区（0xC00000）可容纳，剩余约 478KB。

## 2026-10-31 深夜补充：提示音实机缺陷三轮修复与断线自愈

第一版提示音随应用固件烧录后，本地链路检查（`tools/chime_device_check.py`：触发 thinking 状态并同步抓取设备 mic/reference/clean 三通道波形）暴露提示音只播出约 100ms。串口日志（PowerShell System.IO.Ports 抓取，未装新依赖）定位：**提示音块与 playback_task 的预缓冲逻辑竞态**——chime 分支不设置 shown_generation，块 2 播完后循环重新进入"队列<5 且无结束标志"的永久等待；第一版计数修复仍自锁（等待 pending 归零，而消费 pending 的正是被卡住的播放任务，串口日志 `chime_play pending=0 queue=0` 与 `chime_enqueued blocks=6` 相隔 20ms 是铁证）。

最终方案（结构性）：**提示音完全脱离音频队列**——首次播放时合成 6000 样本到 PSRAM，由独立短任务 `chime_task`（8KB 栈，与 TTS 同款 `audio_play_pcm24` 逐块播放），与 playback_task 的预缓冲彻底无关。设备端复测（`evidence/chime-check-final2-20261031.json` + WAV）：双音完整（988Hz 与 1319Hz 能量为基线 3 个数量级以上，250ms 依次播出）、`queue_depth` 全程 0、播放后增益干净恢复待机、无任何卡死。AEC 参考随播放链对齐（mic 收到回声、clean 残差降低），提示音不会污染唤醒与插话判定。

过程中还发现并处理了**独立的断线自愈缺陷**：对端进程死亡可能留下 TCP 半开连接，设备侧 WS 事件与传输层超时都暴露不了，表现为设备永远不重连（昨晚的设备检查流程其实踩过，靠硬复位恢复）。`ping_interval_sec`/`pingpong_timeout_sec` 配置实测改变不了该行为。最终实现应用层心跳：设备每 30 秒发 `device_ping`，bridge（`assistant_runtime.py` NativeDevice.handle）回 `device_pong`，设备超过 240 秒无任何下行就 `esp_restart()` 自愈（240 秒覆盖现有 barge 真人测试 150 秒时长，不会误杀）。`python -m unittest tests.test_gateway_v1` 11 项通过；设备在新 bridge 下连续 60 秒三次采样保持在线（若心跳无响应早已触发重启）。

## 2026-10-31 终章二：AEC/NS 增强 + OTA 远程升级（牛牛指令）

### OTA 远程升级（端到端已验证）

- **设备端** `ota_update.cpp/h`：bridge 经 WS 推 `{type:"ota", url, sha256}` → 设备 HTTP 下载（Bearer 鉴权）→ 流式写备用 app 分区 + SHA256 校验 → `esp_ota_set_boot_partition` → 重启。新固件 WS 连接成功即 `esp_ota_mark_app_valid_cancel_rollback()`（CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE，未连上 bridge 即回滚，杜绝 OTA 变砖）。
- **bridge 端**：`control_api.py` 新增 `/api/ota/firmware`（token 鉴权返回 build 产物）；`gateway.py` 设备握手时比对 hello 的 `firmware_version` 与本地产物版本，落后即推送。产物版本解析自 bin 的 esp_app_desc。
- **版本机制**：版本号移入 `main/version.txt`，main/CMakeLists 读入并注入 `ASSISTANT_FW_VERSION` 编译定义（`CMAKE_CONFIGURE_DEPENDS` 联动），顶层 `PROJECT_VER` 同源——直接改 PROJECT_VER 不会触发 app_desc 增量重编，这是本次踩过的坑。
- **调试中抓到并修复的两个实机缺陷**：①ota 命令最初误挂在 hello 分支（bridge 发的是独立 `type:"ota"` 消息），设备静默忽略；②OTA 任务栈建在 PSRAM，`esp_ota_write` 冻结 cache 时触发 `esp_cache_utils.c:96` 断言崩溃循环——ESP32-S3 写 flash 期间任务的栈与被访问缓冲必须在内部 RAM，已改内部 8KB 栈。
- **端到端证据**（`evidence/serial-ota-e2e4-20261031.log`）：`ota_command → ota_download partition=app1 → ota_ready bytes=2477920 restarting → 重启 → mn6 加载正常`；分区读回：运行分区 app1=0.2.5，app0 保留 0.2.4 可回退；bridge 推送日志两次（0.2.2→0.2.4、0.2.4→0.2.5），升级到位后不再推送。`tests.test_gateway_v1` 11 项通过。
- **从此固件迭代不再需要 USB 连线**；USB 仅在 OTA 链路本身失效（变砖）时使用。

运行 0.2.5（OTA 升级，非 USB），mn6_cn 模型 + NS/AEC 增强 + 提示音 + 断线自愈全部在线；bridge 运行中设备在线（connected=true, idle）。真人验收项同上节。

## 2026-11-01 续：打断误触发根因与修复（0.2.6，OTA 实战升级）

牛牛确认云端已付费、唤醒正常，但打断有问题。配对设备检查复现：**回答播放中第 4.4 秒发生了一次没有插入唤醒词的误打断**——播放内容经 AEC 的残留被 MultiNet 以置信度 0.1516 误判为唤醒词，穿透 0.12 的打断阈值（candidate→confirmed 仅 21ms，零语音确认）。

修复与验证（`evidence/barge-regress-20261101.json` + 串口日志）：

- 打断阈值 0.12 → 0.30（kWakeThresholdInterrupt）。数据依据：假阳性 0.1516 vs 播放期真词 0.4289，0.30 两侧均有余量。
- **OTA 实战首秀**：0.2.6 经 bridge 推送自动升级到设备（ota_pushed 0.2.5→0.2.6，分区读回 app0=0.2.6 运行、app1=0.2.5 可回退），全程无 USB。
- 回归：同样场景（远端语音播放 6 秒后插入唤醒词）**前 6.9 秒零误打断**，唤醒词插入后 candidate→confirmed 约 600ms（置信度 0.4289）；AEC VERYAGGR 效果量化：echo_floor 6179→1195（降 80%）。
- 待牛牛真人复测：播放中说"你好，小燕子"应稳定打断；若出现"打不断"，串口 `wake_candidate confidence` 数据可用于再校准。
