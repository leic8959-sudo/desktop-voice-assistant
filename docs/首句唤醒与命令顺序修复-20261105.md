# 首句唤醒与命令顺序修复（2026-11-05）

## 实际复现

此前 Chat 后端先调用 `observe_user_text`，但首句还没有通过唤醒验证，观察按门禁返回；随后已经请求模型，直到合成 STT 被输出端消费才确认唤醒。因此“你好，小燕子，打开计算器”会缺少首句控制上下文和记忆刷新。无唤醒词的首句也仍会请求模型；实际工具执行门禁继续拒绝，不能把它描述为已经越权执行真实动作。

主代理使用真实 `ChatBackend`、`VoiceSession` 和真实工具/控制编排，模型、记忆、PC 服务全部替身，实际运行初始 `python -m unittest tests.test_chat_wake_order`：3 项中 2 项失败、1 项通过，0.210 秒，证据 `evidence/chat-wake-order-20261105-before.log`。两项失败分别命中首句用户上下文为空和无唤醒仍请求两轮模型；实际工具门禁对照通过。

## 当前顺序与边界

`gateway.py` 将既有字符归一化和前缀判断提取为同一个方法，Realtime 原分段判断复用它。Chat 的首句改为输入预检确认唤醒后，唯一一次观察用户文本并等待记忆上下文刷新，随后再次检查回合代数和关闭状态，才启动模型。没有复制口令正则或放宽尾音、PC 动作授权。

输出门禁和 Chat 预检共用固定的 10 秒截止时刻；真正云端连接就绪后开始，握手耗时不计入。测试或直接构造场景在首次门禁使用时初始化；后续片段、取消或重新采音都不续期。即使输出消费者尚未调度，迟到的完整唤醒词也不能启动模型。手动按键不要求唤醒，以及已验证后的连续接话继续使用原合同。

Chat 预检持有唯一的有界原文/前缀，沿用 128 事件和 262144 字节限制。未完整的片段只发送带内部验证状态的 STT，不观察或请求模型；完整后合并原文，验证成功的 STT 在观察之前发送一次，让输出门禁及时退出验证等待，模型仍必须等观察完成。Chat 输出端只消费预检结果，不能再把旧片段拼接成另一份授权；Realtime 保留自己的既有分段流检查。

取消、关闭及 `clear_audio` 清除待验证片段，不改变原截止时间。因此输出端已经消费“你好”后发生取消或真实 abort，后续“小燕子打开……”不能借用旧前缀。拒绝片段不会进入模型或工具；已经通过唤醒验证的普通工具权限仍由原工具门禁执行。

监督复核进一步发现输出端统计包含内部验证字段，而预检最初未计该字段，可能先在输出端触发字节拒绝，清理未调度前再被预检接受。主代理单独运行新增终态回归，0.201 秒失败，证据 `evidence/chat-wake-terminal-20261105-before.log`；该场景实际出现两轮模型和替身控制调用，不是实际设备动作。本轮统一事件字节计算，并将拒绝原因保存为会话共享终态：超时、容量、非法转写、缺失唤醒及流提前结束后，不允许取消或重新采音清除拒绝，必须开始新的 VoiceSession。
