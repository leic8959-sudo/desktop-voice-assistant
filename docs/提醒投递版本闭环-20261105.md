# 提醒投递版本闭环（2026-11-05）

## 已复现的问题

原 `claim_due_reminders` 将租约和 updated_at 写入数据库后，从旧查询行构造返回值，仅覆盖租约字段，漏掉新 updated_at。`AssistantRuntime.notifications_loop` 随后直接发送该旧版本快照。因此数据库与通知 payload 版本不一致；固定时刻或系统时间回退时，领取、ACK、稍后提醒还可能不推进版本，使旧记录版本继续匹配。

主代理实际执行初始 `python -m unittest tests.test_reminder_delivery_revision`：6 方法、0.897 秒、6 个失败（包含固定时刻/回退时间两个子例），日志 `evidence/reminder-delivery-revision-20261105-before.log`。真实 SQLite、AssistantRuntime 通知循环、NativeDevice 协议参与回归，设备和时钟全部受控，没有写入真实提醒。

## 设备协议边界

当前固件源码 `control_protocol.cpp:637-645` 只从 notification 读取 title、ID、租约令牌，没有读取 updated_at。显示提醒时会自动发送 notification_ack；初始提醒卡版本为空，“稍后5分钟”禁用。正确 ACK 后，NativeDevice 发送 `reminder_state` 的权威 updated_at，固件更新该卡 revision 后才启用稍后提醒。因此旧快照是真实问题，但不能据此声称当前 0.3.14 的稍后提醒按钮必然失败；原 ACK→权威版本→稍后提醒的设备对照在修复前已经通过。

ACK 只代表提醒已显示/确认交付，不把任务改为 completed。ACK 后旧 claim 版本应拒绝稍后提醒；客户端需使用 ACK 返回的 `reminder_state.revision`，其他客户端刷新实际任务记录，不能放宽 CAS 使旧请求跨版本执行。

## 最小修复

仅修改 `assistant_core/store.py`。新增私有 `_next_task_revision(previous, now)`，沿用 reschedule 已有的 `max(now, previous+1微秒)` 策略，复用于领取、ACK、稍后提醒和既有改期；不改变完成、取消或记忆写入。

领取结果使用同一批 UPDATE 的真实 updated_at 值返回，不增加每行查询。没有显式 now 时，在取得写事务后才读取当前时间；显式 now 保留已有调度/测试合同。租约截止时间和提醒到期时间仍基于实际 UTC current，不把单调逻辑版本当成业务时间。

ACK 在写事务内读一次 now，同时用于租约有效期和新版本；锁等待后已经过期的租约不能使用锁前时间被确认。稍后提醒也在事务内取得实际 now，再计算真实 due_at。旧租约令牌、旧 claim 版本及旧 ACK 版本均继续拒绝重放，不补偿、自动重试或修改设备协议。
