# 音乐候选选择完成合同（2026-11-06）

牛牛明确复现的目标尚未被上一版满足：父代理全量637项通过、禁止外部连接的检查也通过，但最终冻结源码的真实模型对“随便来一个放就行了”仍口头答应而不调用play。因此上一版没有部署。本轮增加只针对真实歌曲候选选择的结构化完成合同，不恢复中文关键词判断，不增加第二NLU模型或通用框架。

## 限定状态与行为

- 状态只来自当前VoiceSession一次实际music_search返回的最多5个真实候选及TTL，上限600秒；记录来源epoch和input_turn_serial。第一次列版本的模型回包不会触发，后续真实用户输入轮推进才进入选择阶段；Realtime response可能早于最终ASR，必须等该输入的accepted epoch也推进才补决策。
- 普通模型已返回工具时，沿原唯一执行入口，不补决策也不重试动作。只有候选选择轮response.done=completed且没有任何工具调用时，允许同一主模型至多一次结构化补决策。
- 写工具仍是music_play/music_queue，selection_id限定实际候选并由服务校验session/TTL。新增music_selection_decision仅有cancel/clarify/unrelated三个非播放结果；取消/转话题清选择状态，澄清保留候选供下一输入。required补决策必须恰好一次，混合play+cancel、双play、未注册动作整批在执行前拒绝。
- 选择轮的普通预答音频和文字直接抑制/丢弃，不保存PCM也不下发，以免“口头说播放”当成已执行。事件累计最多512个、序列化总字节最多2MiB；超过上限可见失败。只有真实工具返回后正常模型回包才可继续出声，scheduled仍只表示安排，instructions保持“准备播放”合同。

## Realtime协议与恢复

父代理实际接口证据：response.create携带tools和tool_choice=required，返回completed但calls为空（music-required-parent-provider-probe-20261106.json）；session.update设置相同tools/required，收到session.updated明确回显后再普通response.create，返回合法cancel（music-required-parent-session-provider-probe-20261106.json）。不通过反复重试取一个绿结果，也不推断所有response override均无效。

实现由music_selection_events的同一个接收者消费ACK，不并发另开WebSocket reader：

1. session.update暂时设置选择工具、required及本轮候选说明。
2. 核对回执tool_choice、工具名集合和instructions精确值，其他memory更新ACK不能代替选择协商，再发response.create。
3. 模型给出唯一有效工具决策后，先恢复原工具集合、auto和原正常instructions，等待恢复ACK。
4. ACK通过才把决策response.done交原工具执行入口。音乐输出在恢复后的普通回应阶段处理，不把force状态留给下一轮。

force期间refresh_memory_context只暂存同epoch的最新instructions，恢复时使用最新版本；恢复中又有更新则补发最新instructions。epoch/generation变化不放行旧选择。模式切换/恢复有8秒ACK期限；无法协商、矛盾或未注册决策仍明确拒绝。补决策期间收到新的speech-start会结束本次选择，由VoiceSession.run收尾关闭该云会话；下一次唤醒建立新会话，不能继承required配置。这一边界保证不执行旧选择，代价是用户需重说被打断的新请求，不能声称同会话无缝继续。

Chat在同一_run_turn、同一主模型/上下文中至多补一次required请求，包含同一个非播放选择工具；选择轮暂不开TTS，完成工具后才恢复普通回复。Qwen/DeepSeek请求形状有隔离检查；本轮真实接口证据仅覆盖Realtime，不能把它当两个Chat provider实测通过。

父完整入口首次检查中，原版与代选均实际通过一次music_play，文字均“准备播放”；但否定普通回包无call，补required后仍无call，导致会话失败。后续保存完整诊断的相同否定case则经过required ACK→decision(cancel)→auto ACK正常完成。这些互相不同的真实结果均保留，说明provider required不能作为百分之百结构保证，不能以最后一次绿覆盖此前漏调用。

最终仅对“补决策completed仍无call”增加确定性零动作收尾：锁住本input所有execute_tool入口，恢复原session模式并确认ACK，再显示“本次没有播放歌曲。如需播放，请再说一次歌名或版本。”，正常listening完成；不再请求模型或TTS、不重试写动作，也不把确定零写标为unknown。Chat同样最多两次决策请求后本地反馈，下一真实输入才解除该input封锁。此证据是“协议缺决策、实际零写”，不是“模型理解了否定并正确选择cancel”；用户正向请求若同样遇到provider漏决策，也只如实未播放，不能假称任务完成。
