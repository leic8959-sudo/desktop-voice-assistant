# 模拟导航语音直达修复

牛牛反馈语音下达“模拟导航”仍未启动。08:12:28与08:12:35自然使用日志均正确识别“模拟导航”，随后回复“准备开始模拟导航”，却没有任何 `navigation_demo_scheduled` 或 `navigation_demo_started` 记录。模型没有调用工具，现有注册工具与提示词不足以保证执行。之后触发电脑/空调兜底并访问失败的本机8123家居服务，只是无关分支，不是导航启动入口。

此前真实文本测试确实调用了工具、后台演示也播放通过，但没有覆盖“ASR识别成功而模型只口头答应”的情况。本次修复该缺口。

## 修改

- `navigation_demo.py` 抽出共用 `is_navigation_demo_request` 判断，保留同样的明确模拟/演示请求范围与否定、引用、翻译、原因询问排除。
- `gateway.py` 在既有真实用户输入校验通过后直接登记该演示请求，不再把是否执行交给模型决定。仍复用原服务和会话退出交接；模型后续调用同一工具会返回已有登记，不重复创建任务。
- 已直接分派的演示设置当前控制已处理标记，不再补跑电脑/空调兜底。新输入会取消原待交接请求，原唤醒词校验、尾音防护、用户输入隔离保持原样。代码记录本次人工决策。
- `tests/test_navigation_demo.py` 补充真实音频识别事件的入口、没有模型工具调用仍登记并交接、与模型工具共用任务、否定/引用不触发、新输入取消。

## 验证

`python -m unittest tests.test_navigation_demo tests.test_wake_ack tests.test_chat_wake_order tests.test_voice_control tests.test_unknown_tool_chain`：60项通过，日志 `evidence/navigation-direct-dispatch-regression-20261106.log`。

加载后使用已有TTS合成1.45秒“模拟导航。”，转为16kHz PCM，经已认证 `/debug/ws` 音频输入、提交到真实Qwen Realtime识别，未直接发送识别文本或调用后台演示API。08:16:00识别为“模拟导航。”，同一时刻出现 `navigation_demo_direct_dispatch ... status=scheduled`；模型随后工具调用复用该任务，回复“准备开始模拟导航”。08:16:03对话结束后 `navigation_demo_started`，实体设备开始播报。

音频及证据：`evidence/navigation-direct-command-20261106.wav`、`evidence/navigation-direct-real-audio-20261106.json`。这覆盖ASR到实际演示链路，未覆盖真人麦克风声学识别。首次验证脚本在释放TTS collector后才复制音频，导致发送空音频并收到云端错误；已改成先复制bytes再释放，成功验证来自后一次1.45秒有效输入，不能把空音频失败视为产品导航故障。

本次最终七步全部发送完成，并收到七次设备播放统计。第二步有2次欠载、第七步有1次，其余步骤为0，全部无溢出；这表示过程中有短暂缓冲不足，不能宣称全程无卡顿，但导航已实际启动并走完七步，没有停在“准备开始”的口头回复。
