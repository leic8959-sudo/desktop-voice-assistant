## 已确认的条件

现有五项 PCM 缓存载荷下限为 533376 字节，还未计结构字段、任务栈、模型、AFE／AEC、TLS、显示和 DMA。仅将 WebSocket 数据编码为 Opus，不改变这些 PCM 存储，不能解决当前 RAM 问题。需要同时设计以压缩帧为单位的有界缓存、代次隔离和发送队列，再验证整个阶段峰值。

固定小智 v2.5.2 来源的 manifest 使用 `espressif/esp_audio_codec ~2.5.0`，audio_service 直接调用 `esp_opus_enc_*`／`esp_opus_dec_*`。本轮读取官方 registry 的 2.5.0 README，其仓库固定为 esp-adf-libs `3bb83597d07b604e1ab5b78dd4370a28d6fa802d`；取得完整非截断 tree，并按 Git blob 核对七份头文件、组件 manifest、CMake 和许可。仅保存到 evidence 作参考，未下载预编译库或组件压缩包，未安装至 managed_components。

2.5.0 README 列 C3／C5／C6 支持，头文件支持 16kHz 单声道及 20ms 帧，但参数必须按组合检查。例如头文件中的 24kHz／20ms 编码码率下限为 40kbps，不能把上行 16kHz 的码率直接套给 24kHz 下行。README 的性能表使用 ESP32-S3、48kHz 双声道、90kbps 等条件，其 heap／CPU 数字不能作为 C3／C6 的资源证明，也不含所有任务栈。

该组件为 Espressif Modified MIT，限定与 Espressif 产品结合使用，不能当成不带条件的通用 MIT 库。候选用途是 ESP 芯片固件；服务端继续使用项目已有 PyAV／OpusBridge，不将 ESP 专用库移入 PC。

## 协议复用边界

项目已有 `audio_codec.py::OpusBridge`，用于旧小智 v1 连接；但原生入口 `handle_native_device` 只接受 PCM16k mono，并创建 `raw_pcm=True` 的会话。直接改用旧 Opus 入口会丢失原生的设备绑定、完整唤醒片段、自然插话协商和媒体控制语义，不能这样登记支持。

可继续研究的方向是：在认证后的原生连接上明确协商编解码参数；边界层把上行压缩帧还原为原控制／ASR会话所需的 PCM，将下行 PCM 编码给已声明能力的设备。唤醒片段统计必须按解码后的有效样本计数；不能将编码字节数冒充 `audio_bytes`。

完整接入还必须处理：

- 编码器 lookahead、尾帧补零和有效样本数，不能让首句字节核对、结束标记或识别头部失真。
- 前导压缩缓存与解码器预测状态；不能假设从任意 Opus 包开始解码都与连续流相同。
- 取消、插话、重连和新会话的代次／编解码器复位，禁止旧包进入新语音会话。
- 帧时长、解码后大小、单包与队列上限、超时和实际时长；不接受任意输入令解码或内存工作量无界增长。
- 真实 C3／C6 的编码耗时、库堆／栈、AFE／AEC、TLS 和整机峰值，以及模型／双 OTA 的 Flash 预算。

本机固件缓存没有 esp_audio_codec。若采用该路径，新增依赖仍由牛牛安装；当前没有改项目清单，也没有用虚构头文件、空实现或 S3 组件链接结果替代目标验证。

来源与文件摘要在 `evidence/opus-memory-research-20261112/`。没有进行 Opus 目标构建、编解码运行、声学、ASR 或实机验证；没有新增板型入口或改变任何适配通过计数。
