# 自然语言控制与空调执行顺序（2026-11-05）

## 已核实的问题

1. 完整语音“电脑打开计算器，计算一加一等于几。”仍被PC守卫拒绝。用户在上一轮播放结束约0.8秒后接话，自动记忆的保守尾音标志同时挡住了执行授权文本，上一轮的分句关键词补丁不能解决这一点。
2. 后续“打开电脑的计算器。”和“三十秒倒计时”等请求出现仅口头承诺、没有相应工具调用的记录。进程启动、API接受请求和语音端到端执行必须分别确认。
3. Home Assistant记录小米返回“设备在当前状态下无法执行此操作”；真实空调为`off`，只发送了`set_temperature`。现有能力目录遗漏空调已经报告支持的TURN_ON/TURN_OFF（特性128/256），妨碍规划开机后调温。

## 当前修改

- `gateway.py`：移除上一轮开应用分句关键词衔接。真实人声经现有VAD时长与尾音检查后，单独取得控制资格；自动记忆继续使用原保守标志。
- 新增`src/assistant_app/application/voice_control.py`：复用已配置的文本模型和`complete_text`封装，从当前用户发言及至多两条、12秒内的用户片段理解意图。模型只可计划现有四类PC动作、实际授权空调的主能力，最多4步；不增加任意命令、键盘输入或鼠标点击。
- 能力目录采用真实设备状态、参数枚举、温度范围和步长。整份计划在任何写入前完成校验，执行仍走既有服务；模型返回未知工具、未知设备、越界参数或非法结构时拒绝执行。
- 明确“开空调并设30℃”由模型规划为先开机后调温；未指定模式保留原模式。开机回读未确认时停止后续步骤。本轮结果缓存用于重复工具调用，失败不自动重试；新语音开始后停止旧计划后续步骤。
- 模型只说要执行却没有调用工具时，语义层核对真实请求并完成缺失步骤，然后依据真实回执生成回答。普通聊天、否定、引用和询问原因由语义模型判为不执行，不再依赖固定口令正则。
- `home_control.py`：补齐由设备特性和HA服务共同确认的空调开关机能力，正确回读空调的heat/cool等开机状态；关机调温在本地返回明确前置条件错误。
- `llm_providers.py`：提示模型调用工具并依据回执回答，不猜测Windows权限，不以口头承诺代替动作。

语义解析会增加一次现有文本模型调用，设12秒超时。单个家庭能力目录最多100条、空调最多20台；没有引入依赖或新的长期服务。语义模型仍可能判断错误，需要真实用语验证，不能将模拟回归当作自然语言理解准确率证明。
