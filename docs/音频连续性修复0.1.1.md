# 音频连续性修复 0.1.1

日期：2026-10-29，Asia/Shanghai。

触发：牛牛反馈自有固件播报卡顿、不自然。

## 确认的实现问题

1. 设备播报期间持续读取麦克风，阻塞读与扬声器写使用同一把codec锁，导致播放写入受到挤占。
2. 桥接对每个小包相对等待，Windows事件循环唤醒延迟会逐包累积。
3. 终端收到第一帧立即播放，没有吸收网络和调度抖动的起播缓冲。

## 改动

- 无AEC的当前硬件在播报期间暂停阻塞麦克风读；播放结束后丢弃短暂积压采集，再恢复唤醒或上行。
- 桥接按累计PCM样本计算绝对下发deadline，允许最多80ms前馈，不累加每次sleep的超时。
- 终端累积约5个20ms帧后起播，短回复收到结束标记即可播放；队列仍有容量边界。
- 添加每轮帧数、缺帧、溢出、播放耗时统计，经设备协议记录到桥接日志。
- 本轮只重写0x20000应用分区，保留Wi-Fi、模型和其他分区。旧0.1.0应用已读回备份。

## 实际验证

- 官方ESP-IDF 5.5.2环境编译成功，版本0.1.1。
- COM3真实写入后返回 `Hash of data verified.`。
- 两秒/100个20ms帧的本地协议回归通过，检查下发耗时不逐包膨胀。
- 临时隔离播放检查：6秒低音量合成音，设备报告300帧、underruns=0、overflows=0，设备统计窗口约5952ms（不等于人耳测量，硬件DMA尾部存在缓冲）。
- 检查结束恢复正常桥接服务，设备重连。
