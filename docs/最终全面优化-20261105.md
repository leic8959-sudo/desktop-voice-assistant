## 定性与修复

### 1. 生产缺陷：从未执行的工具被误判"结果待核实"，暂停整轮工具链（已修复）

`tests.test_gmail_api` 红测暴露的级联：模型调用未注册工具（如 `gmail_send`）→ `_execute_tool` 抛普通 `ValueError("工具不在允许列表")` → `tool_error_result` 落入通用分支 `status=unknown` → `tool_result_unconfirmed` 为真 → `_pause_tool_chain`。结果：一个从未执行的确定性拒绝，让同一回合后续全部合法工具返回 `blocked/tool_chain_paused`，模型也收不到精确错误、无法在回合内自我纠正。实测复现：第一个调用抛 ValueError，第二、三个调用返回 paused 结果。

修复（最小面）：
- `src/assistant_app/application/errors.py`：新增 `LocalToolNotAvailableError`（ApplicationError+ValueError 双继承，保持既有 `assertRaises(ValueError)` 合同），code=`tool_not_available`；`tool_error_result` 映射到确定性 `status=blocked`（不触发暂停）。
- `gateway.py` `_execute_tool` 内四处"调用前即可判定、从未执行"的抛点改用类型化错误：未注册工具、未知工作流 → `LocalToolNotAvailableError`；connector/workflow arguments 非对象 → `LocalToolArgumentsError`。
- 明确不改的边界：home_control 前置校验错误（如"空调当前关机，尚未调温"）仍是普通 ValueError → unknown → 暂停。voice_control 计划路径（gateway 480-522 行）的暂停是该路径设计意图（计划已整体验证，步骤失败说明设备实况偏离，须人工核实）；模型工具路径下该语义属已知保守行为，且"先开机后调温"的文档设计走计划预校验，不受影响。留待有真实误伤证据再动。

新增回归 `tests.test_tool_activity::test_unknown_tool_rejection_does_not_pause_tool_chain`（旧代码红）：未知工具拒绝后，同回合 `desktop_timer_status` 仍可正常执行且 `tools_paused` 为假。

## 首音延迟优化：chat 管道 TTS 连接并行预热

已知遗留（`多LLM供应商接入_20261101.md`）：chat 管道首音约 2-3 秒。原实现中 TTS WebSocket 握手发生在首句文本到达**之后**（串行：LLM TTFT → 首句流式出句 → TTS 建连握手 → 合成首包）。改为 `_tts_turn` 在回合开始即创建握手任务与 LLM 流式并行（`chat_pipeline.py::_tts_turn`），首句到达时连接通常已就绪，关键路径少一次完整建连（实测环境通常数百毫秒，属网络相关收益，未以离线数字宣称具体毫秒数）。

边界与语义保持：
- 握手失败且首句已到 → 按原语义抛出、回合失败回滚历史；握手失败但本轮无文本可合成 → 仅丢弃连接不炸回合（原实现此时根本不会建连，语义等价）。
- 取消/关闭时取消未完成握手并关闭已建立的孤儿连接（含 tool-call 轮无文本场景），复用 `_open_tts` 自身的取消清理（既有 `test_cancelled_handshake_closes_owned_socket` 证明）。
- 工具轮无文本时会多一次"建连即关闭"的连接轮换，属可接受代价；换来了文本轮的关键路径收益。
- 未动 `SOFT_FLUSH_CHARS=60` 软切阈值：出句粒度是听感质量取舍，无真人听音验收不改。

新增红绿测试 `tests.test_chat_tts_lifecycle`：`test_tts_handshake_starts_before_first_sentence`（首句未到握手必须已开始；旧代码超时红）、`test_cancelled_turn_closes_prewarmed_socket`、`test_handshake_failure_without_text_does_not_fail_turn`；既有 13 方法断言未放宽，`test_send_failure_cancels_reader_and_closes_socket` 补给 socket 夹具（预热下需要可用连接）。
