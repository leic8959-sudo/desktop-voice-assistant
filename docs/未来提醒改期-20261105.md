# 未来单次提醒改期（2026-11-05）

> 后续范围更新：第十七轮已允许给未定时待办添加未来提醒，复用相同接口与版本校验，详见 `已有待办添加提醒-20261105.md`。下文保留最初改期轮次的实施记录。

本轮增加 `reschedule_task(task_id, expected_updated_at, due_at)`：只允许修改尚未到期、未完成的单次提醒，新时间也必须严格晚于当前时刻并带时区。已经到期的提醒继续使用 `snooze_reminder`；无提醒时间、已完成或已取消的任务拒绝改期。不扩展重复规则、云日历或页面 UI。

## 存储与并发

复用 `AssistantStore` 的单条 `BEGIN IMMEDIATE` 事务、设备隔离查询和统一 UTC 解析。取得写事务后才读取当前时间，避免锁等待期间到期的提醒仍被允许修改。用真实 `updated_at` 比较版本；新版本取当前时间与旧版本加一微秒的较晚者，保证同一时刻或时钟回退时旧请求不能再次成功。

成功后仅更新提醒时间、版本、提醒待投递状态并清除旧租约，保留标题、身份、创建时间、幂等键和 metadata。读回真实保存结果；其他任务不受影响。两个连接同时使用同一旧版本，只有一个能成功。取消原租约后，旧 ACK 必须拒绝；不补偿、重放或自动重试写入。

## 语音、API 与反馈

- 新增共用语音工具 `reschedule_task`。模型先 `list_tasks` 查真实任务 ID 和版本；目标或新时间不明确先问，不猜测 ID、时间或成功结果。
- 新增同源 `POST /api/tasks/{task_id}/reschedule`，请求字段严格限定 `due_at` 和 `expected_updated_at`，沿用已有认证、错误映射及任务结果脱敏。
- 成功后只清除目标的旧运行时通知，失败保留通知。语音及 API 使用“修改提醒时间”的统一屏幕操作，复用真实 `due_at` 反馈并明确待办仍未完成，不解释为固定延后分钟。
