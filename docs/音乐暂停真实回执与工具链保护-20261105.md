# 音乐暂停真实回执与工具链保护（2026-11-05）

## 实际问题与语义纠正

`DeviceMediaStream.pause` 在设备停止确认缺失时会通过真实 `_halt` 超时返回 `state=error`，但原 `InternetMusicService._pause_locked` 直接回传该状态，没有 `status=unknown`。既有未知工具链保护只识别稳定结果合同，不能据该错误状态暂停后续工具；主代理独立复现摘要 `evidence/music-pause-unconfirmed-reproduction-20261105.json` 已记录这一差异。

最近的 `device_position_s` 和 `position_confirmed=true` 表示设备 I2S 曾报告该位置，不表示已经确认暂停点。暂停 ACK 丢失不会让这个最近已报告进度变成伪造；用户下一轮明确要求 resume 仍可按它安排续播。因此本轮没有作废该 checkpoint、禁止明确续播或更改 worker 进度保存，也不把独立复现中一次明确续播当作另一个缺陷。

主代理实际执行 `python -m unittest tests.test_music_pause_unknown`：7 项中 6 项失败、0.669 秒、退出 1，日志 `evidence/music-pause-unknown-20261105-before.log`。测试使用真实服务、DeviceMediaStream、_Playback 和无 pause ACK 的假设备，缩短等待期限使真实 `_halt` 超时；Realtime 和 Chat 的后续歌曲确实被放入模拟队列，不仅是字段断言失败。新明确 resume 的 checkpoint 对照通过。没有真实音源、账号或设备动作。

## 最小修复

仅修改 `src/assistant_app/application/internet_music.py::_pause_locked`。真实暂停结果为 error 时，返回 `status=unknown`、`retryable=false`、固定 `reason=pause_unconfirmed` 和“暂停未确认；最近设备进度不代表已暂停，请先核查实际状态。”重复 pause 遇既有 error 同样返回未知，不自动再次发设备控制。

确认暂停的正常结果补齐 `status=paused`，供页面和 API 审计准确显示；已知 paused/stopped/ended 状态保持真实 status，无 current 时仍为 stopped。没有给所有 state=error 增加全局解释，没有修改未知保护分类、DeviceMediaStream、平台租约、停止修复、worker、持久 bookmark 字段或音乐自然语言授权。

同一用户输入中的后续工具依靠此前已有的 Realtime/Chat 未知结果暂停保护阻止，新真实输入按原合同独立处理。底层晚 progress 覆盖 pause ACK 的候选未在本轮修改：当前固件按播放任务串行处理暂停并停止后续 progress，尚无实际正常固件重排证据；电脑和家居同类路径也不在本轮散改。
