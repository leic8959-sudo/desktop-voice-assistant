# 多 LLM 供应商接入（DeepSeek / 千问文本 / 千问 Realtime）

日期：2026-11-01。改动目标：消除"整条语音链路绑死阿里 Realtime 一条路"的单点依赖，提供可配置、可切换、可降级的多 LLM 供应商能力。本轮全部为 Python 网关侧改动，固件无变化（0.2.6 保持不变）。

## 升级前的不足盘点

| # | 不足 | 本轮处理 |
|---|------|---------|
| 1 | ASR+LLM+TTS+计费全绑在 qwen Realtime 一条链路，Realtime 不可用助手即全瘫 | 三供应商注册表 + 建连失败自动降级 |
| 2 | 无 DeepSeek、无千问文本模型接入能力，无法按成本/能力选择 | chat 管道（ASR→chat→TTS）落地两个供应商 |
| 3 | 无运行时模型切换入口 | `/api/llm` GET/PUT + 面板"大脑"选择器，偏好持久化 |
| 4 | Realtime 供应商状态不可观测 | `/api/status` 暴露 `bridge.llm_provider`、`active_provider`、`llm.items` |
| 5 | qwen3.8 系默认思考模式，文本链路首字延迟高 | `enable_thinking:false` 默认关闭（实测 TTFT 703ms→≈0） |

固件侧已知不足（本轮未动，需牛牛在场实测）：待机漏唤醒机制原因未定位（诊断工具 `tools/wake_device_check.py --capture-audio` 已就绪待录）；播放期自然插话因 MN 推理被拖慢至 76ms 失效（`kNaturalBarge*` 参数保留，需专项 profile）。

## 架构

```
设备(PCM16k) ──► VoiceSession（设备协议/播放节拍/打断/看门狗，不变）
                   │ backend 抽象（统一事件形状）
                   ├─ RealtimeBackend   阿里 Realtime 全双工（原链路，事件透传）
                   └─ ChatBackend       DeepSeek / qwen_chat 共用：
                        ├─ _AsrPump     paraformer-realtime-v2 实时识别（一连接一任务，
                        │               断线重连，重连窗口音频缓存；sentence_end + 静音计时成轮）
                        ├─ _chat_round  chat.completions 流式；HTTP 层失败自动降级非流式重试；
                        │               工具循环（≤4轮），复用 VoiceSession.execute_tool 全部工具
                        └─ _tts_turn    cosyvoice-v2 按句合成（pcm 24k），音频帧以
                                        response.audio.delta 归一化事件回传
```

关键设计：
- **协议对齐**：ChatBackend 输出与 Realtime 事件形状一致（response.created / response.audio.delta / response.audio_transcript.done / response.done / conversation.item.input_audio_transcription.completed），播放节拍、两阶段打断、状态机全部复用，设备协议零改动。
- **轮次检测**：ASR `sentence_end` + `chat_turn_silence_ms`（默认650ms）静音计时；回复期间新语音自然打断当前轮（对齐 realtime speech_started 行为）。
- **历史管理**：会话内保留最近20条消息；被打断的半截回复恢复快照不入上下文；带 tool_calls 的 assistant 消息只存在于当轮请求内，避免悬空 tool 消息导致后续请求 400。
- **降级链**：`provider_chain()` = 当前供应商 + 其余凭据可用者；仅在建连失败时降级，会话中失败仍结束会话（与 Realtime 行为一致）。切换记录在 `last_provider`。

## 配置

`config.local.json` 新增键（全部可选，缺省即 `qwen_realtime` 原行为）：

```json
{
  "llm_provider": "qwen_realtime | qwen_chat | deepseek",
  "qwen_chat_model": "qwen3.8-flash",
  "qwen_chat_thinking": false,
  "deepseek_api_key": "",
  "deepseek_model": "deepseek-flash",
  "deepseek_thinking": "disabled",
  "chat_asr_model": "paraformer-realtime-v2",
  "chat_tts_model": "cosyvoice-v2",
  "chat_tts_voice": "longxiaochun_v2",
  "chat_turn_silence_ms": 650,
  "chat_max_tokens": 512
}
```

- `qwen_chat` 复用 `aliyun_api_key`（兼容模式与 Realtime 同 key）；`deepseek` 需要另配 `deepseek_api_key`，**ASR/TTS 仍走阿里**，故两者都要。
- 供应商偏好持久化在 `runtime/llm-preference.json`（同音色偏好模式，不碰密钥配置），下次会话生效。
- chat 音色白名单为 cosyvoice v2 后缀系列（文档已不再提供裸 `longxiaochun` 等旧 ID）。

## 遗留与边界

- chat 管道延迟高于 Realtime（ASR 断句 + 首句 + TTS 起播，估计 2-3 秒首音），换来更低成本与供应商冗余；追求最低延迟仍用 `qwen_realtime`。
- 播放期 AEC 残音经 ASR 转写理论上可能形成误轮次，与 Realtime 同风险（依赖固件 AEC），需真人实测确认。
- 浏览器手动录音 + chat 管道走 `commit_audio` 即时成轮；自动模式走静音计时。二者已由 mock 覆盖，真人浏览器录音未实测。
- 会话历史不跨会话持久（与 Realtime 行为一致，记忆仍走 memory_store）。
