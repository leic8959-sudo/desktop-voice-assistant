# 音乐停止真实回执修复（2026-11-05）

## 已确认的问题

`DeviceMediaStream.stop` 在设备离线或停止确认缺失时返回 `state=error`，原 `InternetMusicService.action(stop)` 忽略这一结果并固定返回 `status=stopped`。平台停止抛异常时，原流程还会跳过清空及持久保存队列和续播进度，后续歌曲可能继续排入播放。

主代理先增加三个监督回归并实际执行，原逻辑两项失败、一项通过，记录在 `evidence/music-stop-receipts-20261105-before.log`；本轮保留这些断言。

监督复核实际平台实现 `tools/music_assistant_player/provider.py` 的 `release` 发现，租约不匹配时合法返回 `accepted=false`。原 `MusicAssistantClient.stop` 仍会清空本地租约，因此仅检查是否抛异常不足以确认停止。

## 修改后的行为

停止请求先使正在准备的旧播放失效，清除等待请求、当前曲目、队列及续播资格，再持久保存取消意图；设备或平台失败不恢复这些内容。一次受保护的清理任务继续尝试设备停止和平台释放，调用者取消时等待同一任务收尾后再传播取消。

保存失败仍尝试停止两端，记录完整堆栈并将原错误传播给调用方；保存取消时保留“保存未确认”，不误称取消状态已经落盘。设备停止异常不会妨碍平台释放尝试。设备未确认停止、平台异常或拒绝时返回 `status=unknown` 和安全原因码，状态页保留“停止结果待核实”；不会向页面或语音返回原异常中的地址、令牌，也不自动重试停止写入。

真正发出平台停止命令时，只有对象回执且 `accepted is True` 才清除本地租约；拒绝、缺字段或非法类型抛安全 `MusicAssistantError` 并保留租约。无本地租约或旧会话停止请求仍按原合同返回本地 `accepted=false`，不联网。设备与平台正常确认时保持原 `status=stopped` 合同。停止请求取消队列不等于独立物理听音确认。
